# 0.2.6 CPU baseline

Recorded 2026-10-29 on `wip/0.2.6-bench`. The code under test is `1c7c6ea` (release/0.2.6 after the
`main.rs` module split). The harness commit adds only the benchmarks and the voice-relay seam
described below. To measure an optimisation, re-run the same commands and compare medians.
Every raw `BENCH` line is in [`0.2.6-cpu-baseline-raw.txt`](0.2.6-cpu-baseline-raw.txt).

## Machine

- Apple M4, 10 cores (4 performance + 6 efficiency), 24 GiB, macOS 26.4.1 (25E253).
- rustc / cargo 1.97.1, default release profile (no LTO).
- The workstation was shared, not isolated: load average 12–15 during the runs (a VM, Postgres,
  Discord, browsers). Each table entry is the median of 5 runs, and the min–max range shows the noise.
  Process CPU time is less sensitive to load than wall time, but scheduling across performance and
  efficiency cores still spreads single runs by roughly ±10–20%.

## Commands

```sh
# This machine's stable toolchain lacks lib/rustlib/aarch64-apple-darwin/bin/rust-objcopy, so
# release builds fail at the strip step. Turning stripping off does not change generated code.
export CARGO_PROFILE_RELEASE_STRIP=false

# Every benchmark, one pass (each prints `BENCH name=.. ops=.. cpu_us_per_op=.. wall_ms=.. extra=..`):
cargo test --release --locked -- --ignored --test-threads=1 bench_ --nocapture

# One benchmark:
cargo test --release --locked -- --ignored --test-threads=1 bench_voice_gateway_udp --nocapture

# This baseline: 5 passes, medians, then 30 s of idle CPU for the real gateway and client binaries:
python3 scripts/bench-cpu.py --runs 5 --idle 30 --raw docs/perf/0.2.6-cpu-baseline-raw.txt

# Profiling (macOS): run one benchmark for longer, then sample it.
DINMOO_BENCH_SCALE=3 target/release/deps/dinmoo_proxy-<hash> --ignored --exact \
  bench::bench_voice_gateway_udp --nocapture &
/usr/bin/sample $! 5 -file voice-gateway.sample.txt
```

`DINMOO_BENCH_SCALE` multiplies every operation count. Keep it at or below 10 for
`bench_handshakes`, because closed client sockets sit in TIME_WAIT. All traffic stays on loopback.
The Discord host name only appears as a TLS SNI value inside the process. The voice `Ready` IP the
client sees is TEST-NET-3 (203.0.113.1); the bridge rewrites it and never contacts it.

## What is measured

- **Process CPU µs/op**: `getrusage(RUSAGE_SELF)` user+sys for the whole test process over the
  measured window, divided by ops. It includes the in-process load generators (TLS peers, fake
  Discord, fake gateway or client, echo server), so compare it only with itself.
- **Code-under-test µs/op**: CPU of the threads of the runtime that hosts the production code,
  read per thread with `thread_info` (Mach). **This is the number 0.2.6 should move.**
- Setup (TLS and WebSocket handshakes, warm-up packets) falls outside the window, except in
  `handshakes`, where the handshake is the operation.
- Voice "blast" phases keep 128 datagrams in flight, with credit returned by the receiver, so
  loopback UDP never drops. "Lockstep" phases keep one in flight, so each packet crosses every hop
  alone. Real voice traffic (one packet per stream every 20 ms) looks more like lockstep. Every run
  reported `lost=0`.
- Runtimes: the code under test runs on its own multi-thread runtime (default 10 workers, as
  `#[tokio::main]` gives on this machine) unless noted. The harness runs on a separate runtime.

| Benchmark | Production path exercised | Op |
|---|---|---|
| `tcp_tunnel_x1`, `_x8` | Gateway v3 data tunnel: TLS server stream → `session::tracked_data` (one shared client-session `Activity`) → `select!` on cancel / `copy_bidirectional_with_sizes(TCP_COPY_BUFFER_SIZE)` → loopback TCP echo. 256 MiB each way, split over 1 or 8 concurrent tunnels | MiB relayed (both directions summed, 512 per run) |
| `handshakes` | `gateway::serve` → admission → `handle_gateway_connection`: TCP connect, TLS (RSA-2048 fixture), DMPX v1 auth, close. One shared `ClientConfig`, like the client | connection |
| `handshakes_no_resumption` | Same, with client resumption disabled (every handshake is full) | connection |
| `handshakes_ecdsa_p256` | Same, with an ECDSA P-256 certificate (Certbot's default key type) | connection |
| `voice_client_udp_*` | `voice::local::run`: local TLS + WebSocket from a fake Discord (production `VoiceIdentity`), TLS tunnel to a fake gateway speaking `wire` records. `up` = Discord UDP → `UDP_SEND` records; `down` = `UDP_RECV` records → Discord UDP. 1000-byte payloads | packet |
| `voice_gateway_udp_*` | `voice::gateway::relay_with`: client tunnel = TLS server stream in session `ActivityStream` + `wire::framed`; Discord side = TLS WebSocket plus a UDP media socket on loopback. `up` = `UDP_SEND` → media UDP; `down` = media UDP → `UDP_RECV` | packet |
| `socks_udp_frames` | `udp::write_frame` on a split client TLS stream → loopback → `udp::FrameReader` on a split `ActivityStream<TlsStream>` (UDP ASSOCIATE shape). 1010-byte frames | frame |
| `runtime_flavor_{current,multi}_*` | `voice_client_udp` (50 k blast, 10 k lockstep) with the client on `new_current_thread` vs `new_multi_thread` | packet |

### Idle CPU of the real binaries

`scripts/bench-cpu.py --idle 30` runs `cargo build --release --locked`, then starts both binaries on
free loopback ports:

- the gateway (`DINMOO_TLS_CERT_DER`/`DINMOO_TLS_KEY_DER` = fixtures);
- the client (`DINMOO_TLS_ROOT_DER` = `test-ca.der`, gateway `localhost:<port>`, temporary
  `DINMOO_VOICE_IDENTITY_DIR`).

It waits for `client session ready`, settles for 3 s, reads `ps -o time=` before and after a
30-second window, then kills both processes.

| Process | CPU over 30 s idle | CPU ms per s | Lifetime CPU s | RSS MiB |
|---|---:|---:|---:|---:|
| gateway | 0.00 s | 0.00 | 0.01 | 4.1 |
| client | 0.00 s | 0.00 | 0.02 | 4.7 |

Both binaries stay below `ps` resolution (10 ms per 30 s, i.e. under 0.33 ms of CPU per second)
while the control session is connected and heartbeating.

## Seam added for `voice_gateway_udp`

The relay's `ready_endpoint()` rejects non-public IPs, so a loopback media endpoint cannot receive a
grant. The relay also binds its grant socket to `0.0.0.0:0`, which would make the test binary bind
a wildcard address and can trigger the macOS application-firewall prompt. In
`crates/proxy/src/voice/gateway.rs`:

- `GrantScope { allow: fn(IpAddr) -> bool, bind_v4, bind_v6 }` with
  `const PUBLIC_GRANTS = { is_public_ip, "0.0.0.0:0", "[::]:0" }`. These are exactly the old
  hard-coded policy and bind addresses.
- `relay()` keeps its signature and calls the new `pub(crate) relay_with(.., PUBLIC_GRANTS)`.
  `run()` still calls `relay()`.
- `ready_endpoint_with(text, scope)` holds the old body with `(scope.allow)(ip)`. The old
  `ready_endpoint(text)` is now a `#[cfg(test)]` wrapper using `PUBLIC_GRANTS`, so the existing tests
  run unchanged.

Production behaviour is unchanged, and the wire protocol is untouched. Only `crate::bench`
passes another scope (loopback-only, bound to `127.0.0.1:0`). Nothing else in production code
changed. The harness also adds `#[cfg(test)] mod bench;` in `main.rs` and `libc` as a Unix-only
dev-dependency, using the version already locked.

## Where the CPU goes

These are self-time samples from `/usr/bin/sample` at 1 ms intervals, run against the benchmarks
with a raised `DINMOO_BENCH_SCALE`. Shares are of the busy samples on the code-under-test threads,
with idle and parking frames excluded.

- **TCP tunnel (gateway).** Syscalls take about 61%: `recvfrom` 25%, `writev` 20% (TLS records
  out) and `sendto` 16% (plain TCP to the target). AES-GCM takes 23% (encrypt 12%, decrypt 11%) and
  `memmove` 8%. Everything in tokio, rustls state handling and the app is under 3%. rustls reads
  TLS input at most 4 KiB per `read_tls` (`READ_SIZE` in its deframer), so every 16 KiB record costs
  several `recvfrom` calls. With 8 tunnels on one `Activity`, the contended
  `std::sync::Mutex` slow path (`ActivityStream` touch, inside `copy_bidirectional`) is about 5% of
  gateway samples. That matches x8 costing about 8% more gateway CPU per MiB than x1.
- **Handshakes (gateway).** Resumption already happens with a shared `ClientConfig` (300/300). A
  full RSA-2048 handshake costs 4.3× the gateway CPU of a resumed one. In the resumed path, about
  20% is the `eprintln!("session: {e:#}")` line for "peer closed connection without sending TLS
  close_notify": stderr is unbuffered, so each line takes several `write` syscalls and fires once
  per closed connection. X25519 takes about 20% (`fe_mul_impl`, `x25519_scalar_mult`,
  `fe_loose_invert`). SHA-512 compression (HKDF-SHA384 for the preferred
  `TLS13_AES_256_GCM_SHA384` suite) takes about 4%, `getentropy` 4%, and `writev`, `close`,
  `accept` and `setsockopt` the rest.
- **Voice gateway relay.** In the sampled window (mostly the `up` blast), `sendto` (UDP to Discord)
  is 47%. About **25% is `swtch_pri`**: a parking_lot spin-yield in `RawMutex::lock_slow` on
  tokio's **timer-driver lock**, reached from `time::Handle::process_at_time`, `reregister` and
  `clear_entry`. Every `select!` iteration of `relay_with` creates a new `sleep_until(deadline)`,
  and every `control.send` is wrapped in a 15 s `tokio::time::timeout`. That means two timer
  registrations and removals per packet, contending with 10 parking workers. `__bzero` is 2.6%
  (see the next bullet).
- **Voice client bridge.** `writev` is 31% (one TLS record per `UDP_SEND`, since `Framed::send`
  flushes every record), `sendto` 26% (UDP to Discord) and `recvfrom` 16%. `__bzero` takes 4.8%:
  tungstenite's `read_in` zero-fills its read buffer up to `read_buffer_size` (128 KiB by default)
  before every read attempt, and `select!` re-polls `ws.next()` once per packet. AES-GCM is only
  about 3%. `local.rs` also wraps every send in `timeout(WRITE_TIMEOUT, ..)`.
- **SOCKS UDP frames.** The writer (client) spends 79% in `writev`, because `write_frame` does
  `write_u16` and then `write_all`. That produces two TLS records and two syscalls per frame. The
  reader (gateway) spends 52% in `recvfrom`. `FrameReader` reads at most 1502 bytes per call, then
  allocates and `drain`s each frame.
- **Runtime flavour.** A current-thread client runtime uses about 20% less client CPU under blast
  load and about 5% less in lockstep, with no loss and similar wall time. Cross-thread wakeups and
  work stealing are the difference.

### Candidate 0.2.6 changes these numbers can verify

None of these changes alter the wire protocol, because TLS record boundaries are not part of it.

- Reuse one pinned `Sleep` in `relay_with` (reset only when `expires` changes), and replace the
  per-send `timeout` with a single write deadline or watchdog. Do the same for `local.rs`. Target:
  `voice_gateway_udp_*` and `voice_client_udp_*`.
- Set a smaller `WebSocketConfig::read_buffer_size` on both voice WebSockets, or avoid re-polling
  `ws.next()` on every packet.
- Batch voice records with `feed` and one `flush` while more UDP datagrams are ready.
- Encode the SOCKS UDP length and frame in one buffer, giving one TLS record per frame; reuse the
  `FrameReader` buffers.
- Replace the `Activity` mutex with an atomic timestamp (`tcp_tunnel_x8`). Consider a buffered read
  layer under rustls to cut `recvfrom` calls (`tcp_tunnel_*`).
- Rate-limit or downgrade the per-connection "close_notify" error log (`handshakes`), and use
  an ECDSA certificate in deployment.
- Run the client on a current-thread runtime (`runtime_flavor_*`).
