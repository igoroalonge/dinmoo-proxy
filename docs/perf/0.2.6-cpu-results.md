# 0.2.6 CPU results

Recorded 2026-10-29. The comparison is the baseline harness commit `7b7cb7b` (0.2.5-era code after the
`main.rs` split, see [`0.2.6-cpu-baseline.md`](0.2.6-cpu-baseline.md)) against `e7bfa3e`
(`wip/0.2.6-integrate`, the 0.2.6 release candidate). Each build uses its own release profile. Every raw
`BENCH` line is in [`0.2.6-cpu-results-raw.txt`](0.2.6-cpu-results-raw.txt).

## Conditions

- Same machine as the baseline: Apple M4, 10 cores (4 performance + 6 efficiency), 24 GiB, macOS 26.4.1,
  rustc / cargo 1.97.1, `CARGO_PROFILE_RELEASE_STRIP=false`.
- `7b7cb7b` builds with the default release profile. `e7bfa3e` builds with fat LTO, one codegen unit and
  `panic = "unwind"`. A third build of `e7bfa3e` with LTO off and 16 codegen units separates the profile
  from the code changes.
- The workstation was shared. An unrelated Postgres batch kept 3–4 cores busy for the whole session. The
  runs waited 20 minutes for it to finish, but it did not. With browsers, Discord and a Colima VM added, other
  processes used 4.6–8.3 cores (`ps` %CPU summed) and the load average was 6–15. To spread that load
  evenly, each round ran one pass of every build and rotated the order between rounds. Medians are of 7
  rounds (default workers), 5 rounds (one worker) or 12 rounds (one worker, `tcp_tunnel`).
- The noise is large. Single runs spread ±10–30%, and outliers reach +80%. Treat a change under about 10%
  as noise unless it appears with both worker counts. Every voice run reported `lost=0`, and the
  handshake benches resumed 300/300 and 0/300 as in the baseline.

```sh
export CARGO_PROFILE_RELEASE_STRIP=false
git worktree add <tmp>/bench-base 7b7cb7b      # before; HEAD is after
cargo test --release --locked --offline -- --ignored --test-threads=1 bench_ --nocapture
# HEAD without LTO:
CARGO_TARGET_DIR=<tmp>/target-nolto CARGO_PROFILE_RELEASE_LTO=false \
  CARGO_PROFILE_RELEASE_CODEGEN_UNITS=16 cargo test --release --locked --offline -- --ignored ...
# One tokio worker, the production gateway's shape on a 1-vCPU VM (it also shrinks the harness runtime):
TOKIO_WORKER_THREADS=1 cargo test --release --locked --offline -- --ignored --test-threads=1 \
  bench_tcp_tunnel bench_handshakes bench_voice_gateway_udp bench_socks_udp_frames --nocapture
python3 scripts/bench-cpu.py --runs 0 --idle 30  # in each tree
```

### Benchmark mapping

No benchmark was renamed or added. Where production changed, HEAD's harness follows it, so each side
measures its own production path:

- the gateway-side accepts in `tcp_tunnel` and `socks_udp_frames` go through `gateway::buffered`;
- `handshakes*` use stateless session tickets, as `gateway_tls` now does;
- `voice_gateway_udp` uses `wire::websocket_config()`;
- the `voice_client_udp` warm-up starts with an IP-discovery datagram. This is setup and falls outside
  the measured window.

The shipped client changed runtime: 0.2.5 used `#[tokio::main]` (multi-thread) and 0.2.6 uses a
current-thread runtime. The "client as shipped" rows therefore compare `runtime_flavor_multi_*` on
`7b7cb7b` with `runtime_flavor_current_*` on HEAD (same op counts). `voice_client_udp_*` keeps a
multi-thread runtime on both sides, so it isolates the code changes.

- **Clear wins.** The voice relay under burst load improved most: the gateway uses 25–58% less CPU and
  the client 15–56% less. Batching several datagrams into one TLS flush, the single pinned grant `Sleep`
  and the 16 KiB WebSocket read buffer account for this. The SOCKS UDP path uses 34–38% less on both
  sides (one write per frame and a borrowed `FrameReader`). The downlink burst and SOCKS UDP gains hold with either worker count. With one worker, the uplink
  burst gain shrinks to −9%.
- **Smaller wins.** Lockstep voice, one packet in flight, uses 10–16% less gateway CPU and 7–21% less
  client CPU. With one worker, gateway uplink lockstep shows no change.
- **No measurable change.** For TCP tunnels, the default-worker result is −10% to 0% and the one-worker
  result is +2% to +8%. Both are inside the noise, and the min–max ranges overlap almost completely. The
  lock-free `Activity` and the buffered accept do not show up on loopback. For handshakes, resumed RSA is
  −4% (default) or −15% (one worker), ECDSA is −9% or −11%, and full handshakes are unchanged. The
  per-connection log line is gone, but stateless tickets add ticket encryption to every handshake.
  These benches do not separate the two effects.
- **LTO.** HEAD versus HEAD without LTO is within ±5% on the burst and throughput benches. On lockstep
  voice, the current-thread client and resumed handshakes, LTO is 1–13% lower. In the one-worker `tcp_tunnel` runs,
  LTO is 5–7% higher, also inside the noise. Nearly all of the change above comes from code, not from
  the profile.
- **Runtime flavour.** At HEAD, the paired current-thread vs multi-thread client difference is
  +1.4% (up), −18.8% (down), −6.8% (up lockstep) and −3.5% (down lockstep), against −24.5%, −18.6%,
  −5.9% and −5.6% at `7b7cb7b`. Uplink batching removed most of the cross-thread wake-ups that made
  the multi-thread runtime expensive there.

## What this means for the ~18% gateway CPU in production

The production gateway runs on one x86_64 vCPU, so it gets one tokio worker under both 0.2.5 and 0.2.6.
Idle CPU stays at `ps` resolution, so the ~18% comes from traffic. On loopback, 0.2.6 makes the voice
relay and SOCKS UDP clearly cheaper per packet: 25–58% less in bursts and up to about 15% less with
one packet in flight. Per-op cost for TCP tunnels and handshakes did not change measurably. Real voice
arrives one packet per stream every 20 ms, which looks like the lockstep rows, where batching rarely has
a second datagram to add. Expect the voice share of production CPU to fall by roughly a tenth, not by
half.

These benches cannot show what probably dominates on the VM:

- kernel and virtio networking, charged to softirq and the hypervisor rather than to the process;
- x86 AES-GCM and syscall costs;
- steal time;
- real RTTs and session counts;
- DNS, now cached for 30 s;
- full handshakes from new or reconnecting clients and scanners.

As a scale check, if the 18% is of the single vCPU, it is 180 ms of CPU per second. At the one-worker
M4 costs above, that would take about 150 MiB/s of tunnel traffic (both directions summed), about 6,000 lockstep voice packets/s
or about 120 full RSA handshakes/s. So either the VM's per-op costs are several times the M4's, or most
of the load is work these benches do not exercise. A realistic expectation is somewhere between no
change and about 15% less gateway CPU, more if voice arrives in bursts. Only measurement on the VM can
settle it: compare the gateway's CPU time (`systemctl show -p CPUUsageNSec` deltas, or `pidstat`) over
comparable traffic windows before and after promotion.
